# Tessera Language Specification v0.1

> Oct 22, 2026 · Sebastian Buza · Status: **draft, pre-M0**. Nothing here has been compiled or benchmarked.
> Amendments: §8 package resolution is superseded by [packages.md](packages.md) (git-native, no central registry). Known gaps → [open-questions.md](open-questions.md).

## 1. Purpose and principles

Tessera is a declarative, deterministic language for the logic layer of applications: you declare types, rules and laws, and the compiler derives the implementation and proves the laws or returns a counterexample. Normative words: MUST, SHOULD, MAY.

| # | Principle | Why |
|---|---|---|
| P1 | Same state and same inputs MUST give the same outputs on every backend. | Lets a solver verify AI-written code instead of trusting it. |
| P2 | The core has three concepts: type, rule, law. | Small grammar means fewer wrong outputs from models. |
| P3 | No ambient effects. Time, randomness, IO and secrets are declared needs. | Power is visible in a header; runs can be mocked and replayed. |
| P4 | Humans review types, laws and examples. Machines write rule bodies. | Review effort goes where errors are costly and text is short. |
| P5 | Errors are counterexamples (concrete failing inputs), also as JSON. | Gives an agent something to act on, not a vague message. |
| P6 | Local reasoning: no global mutable state, declaration order is irrelevant. | An edit cannot silently change distant code. |
| P7 | One canonical text form and one content hash per definition. | Exact caching, semantic diffs, reproducible builds. |
| P8 | The interpreter defines the semantics. Every backend MUST match it bit for bit. | One oracle makes differential testing possible. |

Non-goals for v0.1: systems programming (raw pointers, custom allocators), hard real-time, pixel-level UI control, general scripting, JIT compilation, shared libraries.

## 2. Lexical rules and grammar

Source is UTF-8, braces delimit blocks, and whitespace is insignificant apart from token separation and the lexical rules for comments, strings and literal boundaries below (in particular, contiguous dates versus subtraction). Why: models edit whitespace-insensitive code more reliably, and one canonical formatter removes style choices.

**Termination (G3):** a module header, every simple statement, every non-block declaration (including `use`, `type`, `state`, `needs`, `view`, `law`, `prove`, `example`, `fixture`, `output` and `store`), and every simple surface or app wiring clause MUST end with an explicit `;`. This includes the last item before `}` or end of file. Newlines, `}` and end of file MUST NOT insert a terminator. Block-bodied `rule`, `surface`, `scope`, `comptime` and `app` constructs end at their own closing `}` without an extra `;`. A brace belonging to a record, type or expression does not terminate its enclosing declaration or statement: `type Pair = { a: Int, b: Int };` still requires `;`.

A semicolon is termination punctuation only outside strings and comments, and only after the complete simple form. It MUST NOT split an unfinished expression or stand in for commas in argument lists, collections or records. Nested delimiters and comments do not create implicit statement boundaries. Newlines never decide whether an expression continues: a call can continue across a newline, including before `(`, and an assignment's `unless` suffix can start on the next line before its `;`.

Boundary examples below specify grouping, not a complete expression grammar (`formula` is specified in §2.1; the G2 word classifications and construct boundaries are specified in §2.3). These are valid statement sequences inside a rule:

```tessera
a = b; c = d; // two assignments on one line

a = b;
c = d; // the same two assignments across lines

a = f
  (b,
   c); // one assignment whose value is f(b, c)

a = b
  unless p; // one assignment with the suffix unless p
unless = d; // a separate assignment to the contextual identifier unless
```

These sequences are invalid, not alternative groupings:

```tessera
a = b c = d; // missing ; between assignments

a = b
c = d; // a newline does not supply the missing ;

a = f(b; c); // ; cannot replace an argument comma

a = b +; // ; cannot complete an unfinished expression
```

Likewise, `rule f() { a = b }` and a file ending in `state n: Int` are invalid: neither `}` nor EOF supplies the missing `;`. In `a = b; unless = d;`, the first `;` prevents `unless` from being a suffix; without that boundary, `a = b unless = d;` is invalid, not two assignments.

- **Comments:** `//` to end of line. No block comments.
- **Names:** `snake_case` for values, rules, views and states; `PascalCase` for types and variants. An identifier character is a letter, a digit or `_`.
- **Keywords:** each keyword stands in one position — the grammar fixes it where the production exists, the construct's slot fixes it otherwise. Two kinds, differing only in whether the word may still be used as a name. As of 2026-10:
  - **Reserved** — MUST NOT be used as an identifier. These words introduce or mark constructs, or are reserved for deferred constructs: `module` `type` `state` `needs` `rule` `view` `law` `prove` `example` `fixture` `comptime` `let` `require` `new` `forall` `return` `scope` `use` `store` `surface` `app` `output` `assume` `schedule` `hint` `foreign` `plugin` `never` `old` `exists` `match`.
  - **Contextual** — an identifier everywhere except in the position the table gives, where it is a keyword followed by the token the construct requires. The slot is fixed, so the choice follows from the surrounding tokens, with no lookahead past the construct, and the word stays a usable name — `key` and `index` are plausible field names: `in` `or` `key` `index` `bound` `as` `fail` `fails` `where` `matching` `unless` `is` `sqlite` `migrate` `checked` `http` `cli` `authed` `cookie` `surfaces` `target` `GET` `POST` `then` `idempotent`.

  | Word | Status | Keyword position | As an identifier |
  |---|---|---|---|
  | `return` | reserved | first token of a rule statement | MUST NOT |
  | `scope` | reserved | first token of a scope block inside a surface | MUST NOT |
  | `output` | reserved | first token of an output declaration | MUST NOT |
  | `as` | contextual | after the response expression of a surface clause (`ls => todo.agenda(me.id) as table;`) | yes, except in that position |
  | `bound` | contextual | after the goal of a `prove` declaration | yes, except in that position |
  | `fail` | contextual | after `or` (`let t = tasks[id] or fail NotFound;`) | yes, except in that position |
  | `fails` | contextual | after the call and optional `then` expression of an `example` declaration (`example complete(bob, alice_task) fails NotFound;`; `example f() then x fails NotFound;`) | yes, except in that position |
  | `fixture` | reserved | declaration introducer at module level (`fixture bob: Id<User> = #1 : Id<User>;`) | MUST NOT |
  | `idempotent` | contextual | the goal word after `is` in a `prove` declaration (`prove complete(by, id) is idempotent;`) | yes, except in that position |
  | `in` | contextual | after a quantifier binder (`forall t in tasks`) | yes, except in that position |
  | `index` | contextual | the optional `index` clause of a `state` declaration, after the optional `key` clause | yes, except in that position |
  | `is` | contextual | after an expression, before the variant or goal it tests (`t.status is Done`) | yes, except in that position |
  | `key` | contextual | after the type of a `state` declaration (`state tasks: Table<Task> key id;`) | yes, except in that position |
  | `matching` | contextual | after a type expression (`T matching re`) | yes, except in that position |
  | `or` | contextual | after the expression of a `let` or `require` statement | yes, except in that position |
  | `unless` | contextual | after the expression of an assignment statement | yes, except in that position |
  | `where` | contextual | after a type expression (`T where p`, `new t: T where ...;`) | yes, except in that position |
  | `use`, `store`, `surface`, `app` | reserved | declaration introducers; `use` also begins an app clause | MUST NOT |
  | `sqlite` | contextual | after `=` in a store declaration | yes, except in that position |
  | `migrate`, `checked` | contextual | after the store constructor and after that `migrate`, respectively | yes, except in those positions |
  | `http`, `cli` | contextual | immediately after `surface` | yes, except in that position |
  | `GET`, `POST` | contextual | first token of an HTTP route | yes, except in that position |
  | `authed`, `cookie` | contextual | after `scope`, and in its principal-call argument slot, respectively | yes, except in those positions |
  | `surfaces`, `target` | contextual | first token of an app clause | yes, except in those positions |
  | `output` | reserved | declaration introducer at module level; buffered-append statement introducer inside a rule (§2.3) | MUST NOT |
  | `assume` | reserved | trailing admission marker on a type, law or prove declaration (§2.3) | MUST NOT |
  | `then` | contextual | immediately after the complete call of an `example`, opening its optional observation expression (§2.3); never a statement introducer | yes, except in that position |
  | `schedule`, `hint`, `foreign`, `plugin`, `never`, `old`, `exists`, `match` | reserved | unsupported in v0.1; no source production in any position (§2.3) | MUST NOT |

  Nine words entered the keyword list with the earlier amendment ([#5](https://github.com/developerz-ai/tessera/issues/5)) — `return` and `scope` as reserved, `in`, `or`, `key`, `index`, `bound`, `as` and `fails` as contextual. `fail`, `where`, `matching`, `unless` and `is` were keywords already and are contextual because their slot is fixed.

  G2 is resolved by these classifications and §2.3. Reserved, unsupported words MUST be rejected as syntax, not treated as identifiers or partially parsed constructs. The G4 wiring words are classified above; renderer names (`table`), target names (`native`, `wasm`), binding names (`me`, `sid`), resource names (`time`, `memory`) and the type constructor `Stream` are identifiers, not additional keywords. This resolution does not complete general expression precedence or settle the remaining questions in [open-questions.md](open-questions.md). Words of other expression constructs already classified above retain their classification, including `comptime`, `is` and `in`.
- **Literals (G6, [#10](https://github.com/developerz-ai/tessera/issues/10)):** the lexer takes the longest match at each position, subject to the candidate and boundary rules below. Date, duration and id tokens MUST NOT contain whitespace; text literals (`"..."`) may contain spaces. Integer literals (`42`, `1_000`), decimal literals (`19.99`) and text literals carry no further lexical rule in this amendment. The rules below cover the three remaining literal forms and the one operator they collide with:
  - **Date:** at a token start, a contiguous sequence of four ASCII digits, `-`, two ASCII digits, `-`, two ASCII digits is a date candidate and takes priority over integer/subtraction tokenization, exactly `YYYY-MM-DD`. A valid candidate is one token of type `Date`. It denotes a zone-independent proleptic-Gregorian calendar date, with no time-of-day, not a midnight `Instant`; there is no implicit `Date`/`Instant` conversion (§3). No `Instant` literal in v0.1 (`Instant` comes from `clock.now`, §6). MUST be a valid proleptic-Gregorian calendar date, else `E-LIT-001`. The character after a date token MUST NOT be an identifier character (see **Names**), else `E-LIT-001`.
  - **Subtraction:** `-` is the binary operator whenever it starts a token; the date token is the only exception. `2026-10-22` is one `Date` token; `2026 - 10 - 22` is `Int - Int - Int`; `2026-13-01` is a date token whose calendar check fails (`E-LIT-001`), never a subtraction. Whitespace therefore distinguishes these tokenizations — parentheses (`(2026) - (10) - (22)`) are the escape hatch. A `Date` is never an `Int`, and there are no implicit conversions (§3).
  - **Duration:** an integer literal (magnitude, `_` separators allowed) immediately followed by a unit from the closed set `ns us ms s m h d` — longest unit first, no whitespace between magnitude and unit. Type `Duration`. The character after the unit MUST NOT be an identifier character, so `7d` is a `Duration` and `7days` is an error (`E-LIT-001`), never `7d` plus `ays` or `7` plus `days`. A numeric literal immediately followed by an identifier suffix that is not a complete supported duration (including `7w` or `1.5d`) is rejected with `E-LIT-001`. Fractional durations and calendar units (months, years) are not literals in v0.1. With whitespace, `7 d` is instead an integer and an identifier, not a duration; their juxtaposition is not a valid expression. A unit alone (`d`, `ms`) or inside an identifier (`delay_ms`) is an ordinary name.
  - **Id literal:** `#` followed by ASCII digits, one token. Type `Id<T>`, requiring a unique expected `Id<T>` or explicit ascription; §3 fixes the rule, the ascription `#12 : Id<Task>` — separate expression syntax, not part of the token — and the `E-LIT-002` rejection for missing, ambiguous or incompatible type context.

  Date and subtraction:

  ```tessera
  let due = 2026-10-22;   // one Date token
  let n = 2026 - 10 - 22; // Int - Int - Int
  let m = (2026) - (10) - (22); // parentheses break the date shape
  ```

  An invalid calendar date is rejected, never read as subtraction:

  ```tessera
  let bad = 2026-13-01; // E-LIT-001
  ```

  A date token followed by an identifier character is rejected, never split into a date and a name:

  ```tessera
  let also = 2026-10-22x; // E-LIT-001: identifier character after the date
  let suffix = 2026-10-220; // E-LIT-001: digit after the date
  let leap = 2025-02-29; // E-LIT-001: not a leap year
  ```

  Duration:

  ```tessera
  let grace = 7d;    // Duration
  let tick = 5ms;    // Duration
  let broken = 7days; // E-LIT-001: identifier character after the unit
  let suffix = 5ms2; // E-LIT-001: digit after the unit
  let fraction = 1.5d; // E-LIT-001: fractional duration
  let unknown = 7w; // E-LIT-001: unsupported unit
  let separated = 7 d; // Int then identifier: syntax error, not Duration
  let name = delay_ms; // an identifier, not a duration
  let text = "wait 7 days"; // one Text token may contain spaces
  ```

  Id literal:

  ```tessera
  let t = tasks[#12];        // Id<Task>: the table key column type
  let task = #12 : Id<Task>; // explicit ascription
  let bad = #12;             // E-LIT-002: no expected type
  ```
- **Formatting:** `tessera fmt` output is the only accepted canonical form, and the content hash is computed from the normalized AST, not the text.

Grammar sketch (EBNF; the nine G4 productions delivered in §2.1, the G5 `needs`, capability-reference/list and `output` productions below, the G2 additions and boundaries in §2.3, and the `rule_needs`, `fixture` and `fixture_value` productions below are normative; `types` defines the recursive type-argument list used by `type_expr`, and `scalar_literal` the literal forms used by `fixture_value`. The remaining sketch still requires completion and parser tests):

```ebnf
module     = "module" Ident "@" Int ";" { decl }
decl       = use | type | state | needs | rule | view | law | prove | example | fixture
           | comptime | store | surface | app | output
type       = "type" Ident [ "<" params ">" ] "=" type_expr [ admission ] ";"
type_expr  = record | variant | refined | Ident [ "<" types ">" ]
types      = type_expr { "," type_expr }
refined    = type_expr "[" range "]" | type_expr "matching" Ident | type_expr "where" expr
state      = "state" Ident ":" type_expr [ "key" Ident ] [ "index" tuple ] ";"
needs      = "needs" need_entry { "," need_entry } ";"
need_entry = Ident ":" capability_ref
capability_ref = qualified [ "<" types ">" ] [ "(" [ capability_values ] ")" ]
capability_values = expr { "," expr }
output     = "output" Ident ":" type_expr ";"
fixture    = "fixture" Ident ":" type_expr "=" fixture_value ";"
rule       = "rule" Ident "(" params ")" [ "->" type_expr ] [ rule_needs ] "{" { stmt } "}"
rule_needs = "needs" Ident { "," Ident }
stmt       = simple_stmt ";"
simple_stmt = "let" pat "=" expr [ "or" "fail" Ident ]
           | "require" expr [ "or" "fail" Ident ]
           | "new" Ident ":" type_expr "where" constraints
           | place ( "+=" | "-=" | "=" ) expr [ "unless" expr ]
           | "return" expr
           | output_append
view       = "view" Ident "(" params ")" "=" expr ";"
law        = "law" Ident ":" claim [ admission ] ";"
prove      = "prove" proof [ "bound" bounds ] [ admission ] ";"
example    = "example" call [ "then" expr ] ( "==" expr | "fails" Ident ) ";"
literal    = scalar_literal | IdLiteral
; placeholder: no production in this sketch uses `literal`. It marks the place
; where the literal forms of `expr` plug in; `expr` itself is the existing
; expression facility, not a second expression language (§2.1)
scalar_literal = Int | Decimal | Text | Date | Duration | Bool
Bool = "true" | "false" ; one word — the Bool literal token (`true`, `false`)
IdLiteral  = "#" digit { digit } ; one token — `#` and its ASCII digits
ascription = IdLiteral ":" "Id" "<" Ident ">" ; an expression, not a token
; expr includes ascription as a primary expression (see §3)
fixture_value = scalar_literal | IdLiteral [ ":" "Id" "<" Ident ">" ] | Ident
; a fixture_value is a scalar literal, an id literal — bare `#12`, whose type
; the fixture's declared type supplies (§3), or with its ascription
; `#12 : Id<Task>` (the optional tail above) — or the name of another fixture
; of the same module (§4)
```

**Needs and outputs (G5).** A module-level `needs` declaration contains one or more bound entries. In `listener: net.listen(8443)`, `listener` is the local binding, `net.listen` is the qualified capability name (`qualified` is defined in §2.1), and `8443` is a value-expression argument. A capability reference is not an ordinary rule call: its qualified name MUST resolve to a capability. Optional angle brackets contain a nonempty list of `type_expr` arguments, not declarations of type parameters; optional parentheses contain zero or more `expr` arguments, not types. Type arguments, when present, precede value arguments. Both a bare reference (`Clock`) and explicit empty parentheses (`Clock()`) are syntactically allowed; the AST MUST distinguish omitted parentheses from an explicit empty argument list. Acceptance of a particular name, type/value arity and argument types is a name/type-checking question, not a grammar rule. This syntax defines neither evaluation of capability arguments nor new grant semantics.

No needs-entry, type-argument or value-argument list permits a trailing comma. Each comma separates children only at its own delimiter depth: the comma in `Map<Text, List<Entry>>` is inside that type, and commas in `net.listen(select(port, fallback))` are inside the argument expression, not between needs entries. Nested angle brackets close one type-argument list per `>`; `>>` here closes two nested lists, not a different operator. Parentheses inside a value expression likewise belong to that expression. Missing delimiters or incomplete children are errors; a comma, `;`, newline or EOF cannot repair them. A complete `needs` declaration ends with `;`, including after its final entry.

An `output` declaration binds one name to its declared `type_expr`, so `output ledger: Stream<Entry>;` has name `ledger` and type `Stream<Entry>`. The type MUST denote an output stream under §5–§6; syntactic acceptance alone does not establish that a type is a stream. The declaration does not change commit buffering (§5) or the restrictions on `Secret<T>` (§6). It requires `;` even at EOF. The module-level `needs` declaration binds capabilities; the rule-header `rule_needs` clause selects bindings under §6 and does not declare new ones.

**Rule-header needs.** After the optional return type and before the opening `{`, a rule MAY have one `needs` clause containing a nonempty comma-separated list of binding identifiers. There is no colon, type, capability-reference expression or trailing comma in this list. The opening `{` ends the complete header list; newlines do not end it, and neither `{` nor `;` repairs a missing name after `needs` or a comma. The clause has no terminating `;`: it is part of the block-bodied rule, not a module-level declaration. Omission declares the empty set (§6).

Expressions have no loops. Iteration is through `map`, `filter`, `fold`, `sum`, `count`, `sort_by` and comprehension over collections. Why: no loops removes termination proofs and enables fusion.

### 2.1 G4 syntax and boundaries

The following completes the nine G4 productions. EBNF `{ x }` means zero or more, `[ x ]` means optional, and `|` separates alternatives. Lists shown here are nonempty unless bracketed; no list allows a trailing comma. Quoted punctuation is literal. `Ident`, `Int` and `Text` refer to the lexical names, integer and quoted-text literals above. `expr`, `call` and `type_expr` use the existing expression/type facilities, not a second wiring expression language. `formula` is defined here, with the `law` and `prove` bodies, the proof goal and the goal operator: it is the ninth G4 production and is no longer an open gap.

**Scope of the G4 work order.** [G4](https://github.com/developerz-ai/tessera/issues/8) named nine productions: `store`, `surface`, `app`, `use`, `constraints`, `pat`, `place`, `bounds` and `formula`. This section completes all nine: the eight others and `formula` — the `law` and `prove` bodies, the proof goal `is idempotent` and a cost goal such as `time <= 5ms`. `formula` was an open spec decision (S4/[#14](https://github.com/developerz-ai/tessera/issues/14)); it is settled here against the forms the spec already uses (§4, §5, §10), so the law body, the prove body, the proof goal and the goal operator are defined below and the AST schema freeze is no longer blocked by them. The solver's decidable fragment for laws remains open (D3/[#3](https://github.com/developerz-ai/tessera/issues/3)). G2/[#6](https://github.com/developerz-ai/tessera/issues/6) is resolved separately in §2.3: `assume` has an attachment production and `hint` is reserved but unsupported.

```ebnf
qualified  = Ident { "." Ident }
names      = Ident { "," Ident }
use        = "use" Ident "." "{" names "}" ";"
pat        = Ident
place      = Ident { "." Ident | "[" expr "]" }
constraints = expr { "," expr }
bounds     = limit { "," limit }
limit      = qualified "<=" expr
store      = "store" Ident "=" "sqlite" "(" Text ")"
             [ "migrate" "checked" ] ";"
surface    = http_surface | cli_surface
http_surface = "surface" "http" ":" Int "{" { http_item } "}"
http_item  = route | scope
route      = ( "GET" | "POST" ) HttpPath [ payload ] "=>" handler
             [ "as" qualified ] ";"
payload    = "(" [ payload_fields ] ")"
payload_fields = payload_field { "," payload_field }
payload_field = Ident [ "?" ]
handler    = qualified | call | "(" qualified ")"
scope      = "scope" "authed" "(" principal_call ")"
             "{" { http_item } "}"
principal_call = qualified "(" "cookie" Ident ")"
cli_surface = "surface" "cli" Text "{" { cli_route } "}"
cli_route  = Ident { placeholder } "=>" handler [ "as" qualified ] ";"
placeholder = "<" Ident ">"
app        = "app" Ident "{" { app_clause } "}"
app_clause = "use" names ";" | "surfaces" names ";" | "target" names ";"
formula    = claim | proof
claim      = [ quantifier ] predicate
quantifier = "forall" Ident "in" Ident "."
predicate  = expr [ "=>" predicate ]
proof      = call "is" goal
goal       = "idempotent" | limit
```

**Imports and binding.** Module-level `use` selects one or more exported names from one dependency named in `tessera.lock` (§8 and [packages.md](packages.md)); it does not select a URL or version. There is no wildcard or alias syntax in this production. App-level `use` is a different clause: its comma-separated names refer to modules or stores to wire, not an import selector. A `pat` binds one identifier in `let`; destructuring, wildcard and refutable patterns are not introduced by this amendment. `new` likewise binds its identifier to the created value. A `place` is rooted in declared state; its ordered field and index projections MUST denote writable state, not a local binding, arbitrary call result or computed expression. Thus `tasks[id].status` is a place; `lookup(id).status` is not. Index children are expressions, with their own nested delimiters.

**Constraints and limits.** `new t: T where` consumes a nonempty comma-separated list of Boolean constraint expressions through the statement's `;`; the list means conjunction and may refer to `t`'s fields. In this statement, `where` belongs to `new`, not to the optional refinement of `type_expr`; a refined type with its own `where` MUST be given a named type before use here. The constraints MUST uniquely determine all fields of the new value (§14); unsolvable or ambiguous constraints are compile errors. This syntax does not expand the solver fragment or settle D3. `bounds` is a nonempty list of named resource upper limits, each with one expression child after `<=`. The resource names and limit expressions must type-check as resource limits under §5; the list declares ceilings and states no goal. A `bound` with no limit, a missing right operand or a dangling comma is invalid.

**Formulas, laws and proof goals.** A `law` body is a `claim`: a predicate, optionally opened by a quantifier. A `prove` body is a `proof`: the call under proof, the keyword `is`, and the goal. `forall` is reserved and opens a quantifier — the binder is one identifier, the domain is the name of a `Table` whose rows are quantified over, and the `.` ends the binder and opens the quantified claim. The quantifier scopes over the whole rest of the claim. `=>` is implication inside a formula and chains to the right; in a route clause the same token is the handler arrow, and no production contains both. A goal is either the idempotence marker or a resource limit, so `is time <= 5ms` is the cost goal of §4. A goal is a claim the verifier discharges (§10), while a `bound` limit is a declared ceiling the interpreter checks (§5.7): `is time <= 5ms` claims a limit, `bound time <= 5ms` declares one. Admission is not part of `formula`: §2.3 attaches `assume` to the enclosing declaration, after any bounds. `hint` is unsupported. A formula adds no operator of its own; `expr` and `call` are the existing ones.

**Embedded boundaries.** At delimiter depth zero, expression parsing in these productions stops at the enclosing list's comma or closing delimiter, or at the enclosing statement's `;`. In assignment/let statements, the existing suffix keywords `unless`/`or` delimit the preceding expression; in `new`, the outer `where` delimits the type. In surface clauses, `as` delimits the handler from its renderer; in `prove`, the outer `bound` delimits the goal from the limits; in a claim, `=>` delimits the left operand of the implication and the quantifier's `.` delimits the binder from the quantified body. These tokens inside a nested call, index, record or quoted text do not end the enclosing child. A delimiter cannot repair an incomplete child (`x +;` remains invalid). Calls consume their entire parenthesized argument list; commas there are not outer-list separators. An identifier intended as the whole child at a contextual-keyword boundary can be parenthesized, e.g. `(as)`, rather than consumed as a suffix. The handler slot spells that escape out: `handler` accepts a parenthesized qualified name, so `surface cli "x" { run => (as); }` binds a handler named `as`. The escape exists only where the owning production allows it; this amendment does not extend the expression grammar. Newlines add no boundaries.

**Store and surface lexical slots.** A SQLite constructor takes exactly one quoted text path, optionally followed by the complete pair `migrate checked`; migration semantics are in §7. An HTTP port is a decimal integer token after `:` (no sign or separators), semantically in `1..65535`; whitespace around `:` is immaterial. `HttpPath` is a surface-slot literal: `/` alone or `/` followed by one or more slash-separated nonempty segments. Each segment contains ASCII letters, digits, `_` or `-`. No whitespace or comments may occur *inside* that literal, and it ends before whitespace, `(` or `=>`. A trailing slash, query string, dynamic segment or `//` segment is not part of this minimal syntax. Ordinary `//` comments remain comments, not paths. Surrounding tokens may be separated by whitespace/comments as usual. Paths here are not division expressions. CLI placeholders are the three tokens `<`, `Ident`, `>` in a CLI route's input slot; whitespace between them is insignificant, and they are not comparison expressions. Quoted CLI program names are `Text` literals. Only HTTP and CLI syntax is defined; the later surfaces in §7 remain deferred.

**Surface children and app cardinality.** Payload lists bind their field identifiers for that route; `?` records an optional input. CLI placeholders likewise bind route inputs; duplicate input names in one route are rejected. A bare qualified handler reference (`auth.login`) and an explicit call (`todo.add(me, title, due)`) are distinct syntactic forms: the former selects a handler for generated input adaptation; the latter supplies explicit argument expressions. A parenthesized qualified reference (`(auth.login)`) is the bare form written with parentheses: it names the same handler and exists so that a name coinciding with a contextual word can be written unambiguously. Neither form permits a business-logic statement block. A renderer after `as` is a qualified name, not an extra call or statement. `scope authed` takes exactly one principal call whose argument is a named cookie source; its body contains HTTP routes or nested scopes. It supplies the authenticated `me` binding to enclosed routes (§7); unauthenticated access returns 401. CLI routes do not accept HTTP payload lists or scopes. Empty surface/scope bodies are syntactically allowed. App bodies may be empty, but each of `use`, `surfaces`, `target` occurs at most once; when present its list is nonempty and has no duplicate names. Clause order is immaterial. App surface names refer to declared surface kinds (`http`, `cli` here); ambiguous references are rejected rather than chosen by declaration order.

### 2.3 G2 words, output and admission

All eleven G2 words are classified in §2. The supported additions below use the existing `type_expr`, `expr`, `claim`, `proof` and `bounds` children; they do not define a new expression language or settle G5, S2 or D3.

```ebnf
output        = "output" Ident ":" "Stream" "<" type_expr ">" ";"
output_append = "output" Ident "+=" expr
admission     = "assume"
; decl includes output; simple_stmt includes output_append and stmt supplies its ;
; complete attachment sites (no other construct accepts admission):
type          = "type" Ident [ "<" params ">" ] "=" type_expr [ admission ] ";"
law           = "law" Ident ":" claim [ admission ] ";"
prove         = "prove" proof [ "bound" bounds ] [ admission ] ";"
example       = "example" call [ "then" expr ] ( "==" expr | "fails" Ident ) ";"
```

**Output positions.** At module level, `output` declares one named stream whose element type is the `type_expr` between `<` and its matching `>`; `Stream` here is the fixed type-constructor name, not an arbitrary type. Inside a rule, `output` starts an append statement: its name MUST resolve to a declared output, and its expression MUST have the stream's element type. Only `+=` is supported and it appends one element, not a collection's contents. An append has no `unless` suffix and MUST end with `;`, even before `}`. Its expression extends through nested delimiters to that `;`. It buffers data under §5, never calls a capability or performs delivery itself. Ordinary state assignments cannot target output streams. No output expression, output block or append at module level is supported.

**Admission positions.** `assume` is a single trailing marker immediately before the `;` of a type, law or prove declaration, after any `bound` list. It terminates the preceding complete child at delimiter depth zero; it cannot complete a missing operand. No reason string, argument list, block, prefix form, repeated marker or statement form is supported. On a type declaration it covers proof obligations for refinements in that declaration's right-hand type expression, not obligations in other declarations that use the type. To admit a refinement, name it in a type declaration with this marker; an inline refinement has no admission slot. On a law or prove declaration it covers that declaration's verification obligations. Admission affects only Unknown (§10), never Refuted, and MUST remain visible in `tessera audit`. Executable laws still run at commit (§5), including assume-admitted ones; a false check aborts with `Failed(LawViolation)`. This does not define D3's exact decidable fragment or turn admitted refinements into proven facts.

**Example expression boundaries.** `then` is a keyword only immediately after an example's complete call, before its expected outcome. That call MUST consume its entire argument list, including nested calls and their delimiters. `then` introduces one pure observation expression evaluated against the state after the call completes (the committed state on success, unchanged state on failure); without it, `==` compares the call's success value. The `fails Name` alternative asserts the named call failure, with or without an observation; an observation in that alternative is still evaluated but is not compared to a value. Every argument of an `example` call MUST be the name of a `fixture` of the same module; §4 specifies the declaration and its rules.

At delimiter depth zero relative to the observation, the first `==` or contextual `fails` ends the `then` expression and starts the expected outcome, even across newlines. These tokens inside parentheses, call arguments, indexes, records or strings do not end that child. To put equality inside the observation, parenthesize it: `then (x == y) == true`. To observe an identifier named `fails`, use `then (fails) == expected`; bare `then fails == expected` has an empty observation and is invalid. A `then` inside that observation is an ordinary identifier: there is no second `then` clause. The expected-value expression after `==` extends to the declaration's `;`, respecting nested delimiters; `fails` there is an identifier, not another outcome clause. A failure name after the outcome keyword is exactly one identifier. Empty or unfinished children are errors, not alternative groupings. These are enclosing-production boundaries, not a general operator-precedence specification.

Neither `then expr;` nor `then { ... }` is a rule statement. Because `then` is contextual, `let then = x;` is legal; `then = x;` can only be an ordinary assignment to declared state named `then`, never a transition clause. Likewise, `example then() == x;` calls a rule named `then`; the word is not in its keyword slot there.

**Reserved and deferred.** `schedule`, `hint`, `foreign`, `plugin`, `never`, `old`, `exists` and `match` have no supported v0.1 production: not declarations, statements, expressions, types, quantifiers or proof annotations. They MUST NOT be identifiers. Scheduling source blocks, solver hints, user FFI/plugin declarations, a never type, explicit old-state expressions, existential quantifiers and match expressions are deferred. Snapshot reads (§4–§5), universal quantification (`forall`, §2.1), variant tests (`is`) and built-in trusted capability implementations remain supported without these forms. `hint` cannot admit Unknown or establish Proven; only explicit `assume` provides the admission described above.

Positive syntax fragments (independent, subject to name/type checking):

```tessera

example f() then inspect(g(x == y), tasks[key(fails)]) == expected;
example f() then (fails) == expected;
example f() then then == expected; // observation is an identifier named then
example f() then x fails NotFound;

```

Independent negative syntax fragments:


Before AST freeze, WP A MUST additionally retain an output declaration's name and element type; an append's stream name and expression; the presence and exact span of admission on its owning type/law/prove declaration; and an example's call, optional observation and tagged expected value or failure name. Repeated appends retain source order. There is no `then` statement node or node for a deferred construct. These requirements extend §2.2's inventory, not an existing frozen schema.

## 3. Type system

Types are constraints, not only shapes: a value's type says which values are legal, and the solver uses that to prove laws and delete proven-redundant internal runtime checks. External values still require validation below. Typing is static, structural for records, nominal for ids and variants.

| Type | Meaning | Rule | Why |
|---|---|---|---|
| `Int` | Mathematical integer | Arbitrary precision. `Int[a..b]` has inclusive bounds; a proven range permits fixed-width storage, never different arithmetic (§3 numeric rules below). | No undefined behavior, no silent wrap. |
| `Decimal(n)` | Fixed-point with scale `n` | Values are `k / 10^n` for arbitrary-precision integer `k` and nonnegative compile-time integer `n`; same-scale operations and half-even rounding are defined below. | Money without float error. |
| `F64` | IEEE-754 binary64 | Canonical NaN, no fast-math, fixed evaluation order. | Same bits on every backend. |
| `Text`, `Bytes`, `Bool`, `Date`, `Instant`, `Duration` | Primitives | Text is UTF-8 and compared bytewise. `Date` is a zone-independent proleptic-Gregorian calendar date; its §2 `YYYY-MM-DD` literal has no time-of-day and never denotes a midnight `Instant`. `Instant` denotes a point in time, obtained from `clock.now` (§6), with no literal in v0.1. A `Duration` literal is an integer magnitude with a unit from §2's closed set. | Deterministic ordering and hashing. |
| `T[a..b]`, `T matching re`, `T where p` | Refinement | `p` MUST be in the solver's decidable fragment, or its named type declaration MUST carry `assume` (§2.3). An inline refinement has no admission slot. | Bugs become compile errors. |
| `{ a: A, b: B }` | Record | Structural, immutable. | Local reasoning. |
| `A \| B(x: X)` | Variant (sum type) | Variant tests use `is`; `match` expressions and pattern matching are deferred, with `match` reserved and unsupported (§2.3). | No missing-case bugs. |
| `Maybe<T>` written `T?` | Option | No null anywhere else. | Removes null errors. |
| `List<T>`, `Set<T>`, `Map<K,V>` | Collections | Immutable, with deterministic iteration order (sorted by key or insertion index). | Replayable results. |
| `Table<T>` | Persistent relation of records | Declared with `key` and optional `index`; only `state` may hold one. | Maps to SQL and enables index selection. |
| `Id<T>` | Typed identifier | An `Id<Task>` is not an `Id<User>`. An id literal `#12` has type `Id<T>`, with `T` fixed by the position (see the id-literal rule below). | Blocks mixed-up ids. |
| `Secret<T>` | Sensitive value | Cannot be logged, serialized, compared with `==` or returned from a surface. Only `needs` capabilities (hash, verify) consume it. | Leak prevention checked statically. |

**Numeric rules (S7, [#17](https://github.com/developerz-ai/tessera/issues/17)).** The scale `n` in `Decimal(n)` counts fractional decimal places, not significant digits. Negative, non-integer or non-compile-time scales MUST be rejected. The coefficient `k` has no backend-dependent width limit. All intermediates use mathematical arithmetic; neither `Int` nor `Decimal(n)` may wrap, saturate or overflow merely because a backend selected a machine width. A backend MUST preserve these semantics, including when it chooses wider or arbitrary-precision intermediates.

For two operands of type `Decimal(n)`, `+` and `-` are exact and return `Decimal(n)`. `*` and `/` also return `Decimal(n)`: compute the exact mathematical product or quotient, then round once at that operation to the nearest multiple of `10^-n`. At an exact midpoint choose the result whose integer coefficient is even (nearest, ties to even), symmetrically for negative values. No floating-point intermediate is permitted. Each operation rounds independently; a later operation cannot undo or postpone that rounding. Destination or surrounding result context MUST NOT change division precision or result scale. Comparisons (`==`, `!=`, `<`, `<=`, `>`, `>=`) between equal-scale decimals compare exact values and return `Bool`.

Different scales are distinct types: all arithmetic and comparisons between `Decimal(n)` and `Decimal(m)` for `n != m` MUST be rejected, even when the values are exactly representable at both scales. Mixed `Int`/`Decimal` arithmetic and comparisons MUST likewise be rejected, including `Int` with `Decimal(0)`. There is no implicit rescaling, numeric promotion or inferred wider result scale. This resolution adds no conversion API or decimal literal/ascription syntax.

The following are normative worked examples with operand types stated in prose, not source literal-typing syntax. Except where marked rejected, both operands have the type in the first column and arithmetic results have that same type.

| Operand type(s) | Operation and values | Expected result | Boundary |
|---|---|---|---|
| `Decimal(2)` | `1.20 + 2.30`; `1.20 - 2.30` | `3.50`; `-1.10` | Exact addition and subtraction |
| `Decimal(2)` | `1.20 < 2.30`; `1.20 == 1.20` | `true`; `true` (`Bool`) | Equal-scale comparisons |
| `Decimal(2)` | `1.00 / 4.00` | `0.25` | Exact division |
| `Decimal(2)` | `1.00 / 3.00`; `2.00 / 3.00` | `0.33`; `0.67` | Non-ties below and above midpoint |
| `Decimal(2)` | `1.00 / 8.00`; `3.00 / 8.00` | `0.12`; `0.38` | Positive ties: exact `0.125`, `0.375` |
| `Decimal(2)` | `-1.00 / 8.00`; `-3.00 / 8.00` | `-0.12`; `-0.38` | Negative ties: exact `-0.125`, `-0.375` |
| `Decimal(0)` | `5 / 2`; `7 / 2`; `-5 / 2`; `-7 / 2` | `2`; `4`; `-2`; `-4` | Scale zero still uses half-even |
| `Decimal(2)` | `19.99 / 2.00` | `10.00` | Carry at exact `9.995`; coefficient `1000` is even |
| `Decimal(2)` | `1.25 * 0.10`; `1.35 * 0.10` | `0.12`; `0.14` | Multiplication rounds exact `0.125`, `0.135` once |
| `Decimal(2)`, `Decimal(3)` | `1.20 + 1.200`; `1.20 < 1.200` | Compile-time type errors | No mixed-scale arithmetic or comparison |
| `Int`, `Decimal(0)` | `1 + 1`; `1 == 1` | Compile-time type errors | Equal mathematical values do not imply equal types |

For example, a quotient of two `Decimal(2)` operands remains `Decimal(2)` even when assigned to a destination expecting `Decimal(3)`; that assignment is a type error, not a request for another digit. A statically known zero divisor in decimal division MUST be a compile-time error. If a divisor is not statically known to be zero but evaluates to zero during a call, evaluation MUST abort with reserved `Failed(DivisionByZero)` under §5, never NaN, infinity, wraparound or panic.

**Refined integers and external validation.** `Int[a..b]` contains exactly the mathematical integers `x` with `a <= x <= b`; the bounds MUST be compile-time integers with `a <= b`. Arithmetic on refined integers uses mathematical integer intermediates; any required result refinement is a separate obligation. An internal assignment or call with a statically refuted refinement obligation MUST be rejected at compile time, not clamped or wrapped. An unresolved proof obligation follows §10; `assume` cannot admit a refuted obligation.

External requests and capability results MUST be validated against their declared refinements before they are used as refined values or narrowed into fixed-width storage. A declared external type is not evidence that the input satisfies it. For an external integer outside its declared `Int[a..b]`, the attempted call MUST produce reserved `Failed(RefinementViolation)` under §5, not a compile error, clamp, wrap, panic or successful execution. Validation MUST NOT be waived by `assume` or by trusting an adapter or capability's declared return type. A request rejected at entry MUST NOT execute the rule body. An invalid capability result encountered during a rule MUST abort the whole call, including any earlier proposed writes and outputs.

For a parameter declared `Int[0..100]`, external integers `0` and `100` pass validation; `-1` and `101` MUST produce `Failed(RefinementViolation)`. In contrast, assigning the statically known integer literal `101` to a state of type `Int[0..100]`, or passing it internally to that parameter, is a compile-time error. Fixed-width storage selection cannot change any of these outcomes. These numeric and validation failures remain subject to §11's stable diagnostic codes, exact spans, counterexamples when available, and human/JSON reporting; reserved runtime failure names are not diagnostic codes and do not change the diagnostics schema.

**Id literals (G6):** an id literal `#12` has type `Id<T>`. Without an ascription, the position MUST supply a unique expected type `Id<T>` with one fully determined nominal target `T`: for example, a call argument's declared parameter type, a table's key column type (`tasks[#12]`), an assigned place's type, or a fixture's declared type (§4). The expected type is `Id<T>`, not `T`. Missing context, a non-ID expected type, an unresolved generic target, or multiple conflicting nominal targets MUST be rejected with `E-LIT-002`; the number never selects a target and there is no default target. The compiler MUST NOT choose a target by declaration order.

An explicit ascription `#12 : Id<Task>` supplies that literal's type even without contextual inference. In v0.1 an ascription is legal ONLY on an id literal and never converts, widens or narrows. It is a primary expression, usable wherever an expression is allowed, including call arguments and index operands. The `:` and complete `Id<Task>` belong to the ascription and bind to that literal before surrounding expression operators; `f(#12 : Id<Task>)` and `tasks[#12 : Id<Task>]` need no extra parentheses. Parentheses may enclose the whole ascription, but `(x) : Id<Task>` is not this syntax. This rule does not complete general expression grammar.

An ascribed literal and a previously typed ID MUST still match the surrounding expected nominal ID type. `Id<Task>` and `Id<User>` are distinct, with no implicit conversion; conflicting ascription/context is `E-LIT-002`. Lexical failures in §2 are `E-LIT-001` before type checking; `#12` itself is lexically valid even when its context causes `E-LIT-002`.

These independent fragments assume `tasks` has key type `Id<Task>`, `lookup` accepts one `Id<Task>` argument and returns a value, and the writable states `by` and `number` have types `Id<User>` and `Int`, respectively. Capability use here assumes an enclosing rule declaring `needs clock` and a module binding `clock: Clock`:

```tessera
let t = tasks[#12]; // accepted: unique expected Id<Task>
let found = lookup(#12); // accepted: parameter supplies Id<Task>
let task_id = #12 : Id<Task>; // accepted: explicit target, no context needed
let found = lookup(#12 : Id<Task>); // accepted: ascription is an argument expression
tasks[#12 : Id<Task>].status = Done(clock.now); // accepted: index expression
let missing = #12; // E-LIT-002: no expected type
number = #12; // E-LIT-002: expected Int, not Id<T>
by = #12 : Id<Task>; // E-LIT-002: expected Id<User>, ascribed Id<Task>
```

A generic call `choose(#12)` whose parameter is `Id<T>` and whose other arguments or surrounding context do not determine `T` is rejected with `E-LIT-002`. Likewise, if a position admits both `Id<Task>` and `Id<User>` without selecting one, bare `#12` is ambiguous and MUST be rejected with `E-LIT-002`; `#12 : Id<Task>` supplies a unique target but cannot override an incompatible expected type. A previously typed `task_id: Id<Task>` cannot be passed to a parameter of type `Id<User>` either: that is an ordinary nominal type mismatch, not a lexical failure.

Example:

```tessera
type Qty   = Int[1..100];
type Email = Text matching email;
type Shape = Circle(r: F64) | Rect(w: F64, h: F64);
```

Subtyping: only refinement narrowing (`Int[1..5]` is accepted where `Int[0..10]` is expected). There are no implicit conversions and no user-defined operators. In particular, `Date` and `Instant` are distinct types: neither implicitly converts to the other, and a `Date` MUST NOT acquire a midnight or a time zone from context.

### 3.1 Expression-local variant narrowing (S6)

This resolves [S6](https://github.com/developerz-ai/tessera/issues/16). A variant payload field MAY be projected only where a positive variant fact for that exact value path is available under the rules below. For `type Status = Open | Done(at: Instant);`, `s is Done` tests the tag without reading the payload; `s.at` requires the fact that `s` is `Done`. A missing fact MUST be a compile-time type error, even if a solver could prove the tag by other means. Narrowing grants local payload-access permission; it does not change the declared nominal variant type, introduce a subtype or perform a conversion.

**Stable paths and identity.** A stable path here is a resolved value binding (including a parameter, local binding or quantified row) or state name, followed by zero or more field projections. Path identity requires the same resolved root binding and the same ordered field names. Parentheses around a path do not change its identity. Calls, computed expressions and index expressions are not stable paths for this rule; bind a table lookup to a local value first, as in §4's `let t = tasks[id] or fail NotFound;`. Equal values, equal keys, aliases and similarly named fields do not establish path identity. In particular, a fact about `t.status` says nothing about `u.status` or `tasks[id].status`, even if `t` came from that row. Shadowed names denote different bindings.

**Positive facts and their scope.** The following rules are normative, not general theorem-driven flow analysis:

- A direct positive test `p is V`, where `p` is a stable path and `V` is a variant of its declared type, supplies the fact `(p, V)` when that test is true. Parentheses preserve the test and its facts. No facts are inferred from negation, equality, a Boolean variable, a call's result or elimination of other variants.
- In `A => B`, check `A` with the incoming facts, then check `B` with those facts plus the positive facts supplied by `A`. These extra facts end with `B`; an implication does not itself export facts. If `A` is false, the implication is true without evaluating `B` or reading its payloads.
- Boolean conjunction is written `&&`. In `A && B`, check `A` first, then check `B` with the incoming facts plus the positive facts supplied by `A`. If `A` is false, the conjunction is false without evaluating `B`. When the whole conjunction is true, it supplies the union of the positive facts supplied by its operands. Thus later operands in a conjunction chain may use earlier positive tests, never the reverse. A chain `A && B && C` groups as `(A && B) && C`.
- Facts inherited by an enclosing expression remain available in its nested expressions, but facts learned inside a child do not escape it except through the positive-test/conjunction rules above. A call does not transfer facts to its callee's body or export facts from it; each body is checked independently. Other operators supply no positive facts.
- All extra facts end at the enclosing expression boundary. They MUST NOT flow into a later statement, declaration or independently checked expression. In particular, `let` and `require` do not carry variant knowledge to subsequent statements.

Parentheses explicitly delimit mixed implication/conjunction examples below; these rules do not complete general expression precedence. Ordered conjunction is a typing and evaluation boundary even though its Boolean truth function is commutative. An implementation MUST NOT evaluate a guarded payload projection when its guard is false.

**`unless` and deferred matching.** In `place = value unless predicate;` (also `+=` and `-=`), `predicate` is checked by the ordinary expression rules above, so it may contain locally guarded payload access. The suffix supplies no positive variant fact to `place`, `value` or any subsequent statement: skipping an assignment when a test is true is not a positive guard for that assignment. `match` remains reserved and unsupported in every position (§2.3); this resolution introduces neither match expressions nor pattern arms or destructuring.

**Normative fragments.** The following context declares the types used by the independent fragments below. Assume `tasks` is a `Table<Task>` keyed by `id`; expression fragments have in-scope values `t: Task` and `u: Task`. Rule-body fragments additionally have writable `saved: Instant` and a rule parameter `t: Task`.

```tessera
type Status = Open | Done(at: Instant);
type Task = { id: Id<Task>, status: Status, created: Instant };
```

Accepted payload-access expressions (not claims that these predicates always hold):

```tessera
(t.status is Done) => (t.status.at >= t.created)
(t.status is Done) && (t.status.at >= t.created)
(t.status is Done) && (t.status.at >= t.created) && (t.status.at == t.created)
((t.status is Done) && (u.status is Done)) => (t.status.at >= u.status.at)
```

The first expression narrows only the implication consequent. The next two narrow later conjunction operands in source order. The last supplies two separate exact-path facts to its consequent. A valid rule-body statement is:

```tessera
saved = t.created unless ((t.status is Done) && (t.status.at >= t.created));
```

Here the payload access is inside the predicate's guarded right operand, not in the assignment value. The following independent expressions are rejected:

```tessera
t.status.at >= t.created // no positive test
(t.status.at >= t.created) && (t.status is Done) // test comes too late
(t.status is Done) => (u.status.at >= u.created) // different root
(t.status is Done) => (tasks[t.id].status.at >= t.created) // lookup is not the tested path
```

The following independent rule-body sequences are also rejected, for the stated reasons:

```tessera
require t.status is Done;
saved = t.status.at; // require's fact ended with its expression

let done = t.status is Done;
require done && (t.status.at >= t.created); // Bool bindings do not retain facts

let u = t;
require (t.status is Done) && (u.status.at >= u.created); // no alias transfer

saved = t.status.at unless t.status is Done; // suffix does not guard the value
```

**The `done_once` law.** `law done_once: forall t in tasks. t.status is Done => t.status.at >= t.created;` is well-typed because the direct test grants access to `at` on the identical `t.status` path in the consequent. Rows with status `Open` satisfy the implication without a payload read. This justifies access, not a proof that the timestamp inequality holds. Under §5, commit-time law evaluation binds `t` to rows of the proposed post-state. That is separate from rule-body reads: §4's `complete` still reads its pre-rule snapshot, including its `unless` predicate. Narrowing changes neither snapshot reads nor atomic commit semantics.

## 4. Declarations

Declaration order is irrelevant; the compiler builds the dependency graph. A module is one file and one namespace.

| Declaration | Meaning | Why |
|---|---|---|
| `module todo @1;` | Names the module and its label version. Identity is the content hash. | Versions are labels, hashes are truth. |
| `use auth.{Principal};` | Imports a dependency by name from the lockfile. | Explicit, auditable imports. |
| `type` | Defines a type (§3). | |
| `state tasks: Table<Task> key id;` | Declares persistent state. The only mutable thing, changed only by rules. | One place to reason about change. |
| `needs clock: Clock, rng: Random;` | Declares the capabilities the module requires, binding module-local names to them; it does not give every rule permission to use them. | No ambient effects (P3). |
| `output ledger: Stream<Entry>;` | Declares a typed output stream; rule appends are buffered until commit (§2.3). | No IO before commit. |
| `rule ... needs clock, rng { ... }` | An atomic transition: preconditions, then declared changes, with an explicit capability set referencing module bindings (§6). Omitting `needs` declares the empty set. | Behavior is a checkable state change; required power is a checkable signature. |
| `view` | Pure derived value over state and inputs. May be cached and incrementally maintained. | Enables index selection and incremental evaluation. |
| `law` | Invariant that MUST hold after every rule. | The spec humans review. |
| `prove` | Extra obligation: idempotence (`is idempotent`), bounds (`bound memory <= 1024`), cost (`is time <= 5ms`). | Verified claims about behavior. |
| `example` | Concrete scenario. Runs as a test and seeds generation. | Ground truth for agents. |
| `fixture bob: Id<User> = #1 : Id<User>;` | Declares one named, module-local input value for the `example` declarations of its module. | Every example input has a declared origin. |
| `comptime { }` | Pure, deterministic compile-time generation of declarations. | Replaces build scripts. |

**Fixtures.** A `fixture` declaration names one input value for the `example` declarations of its module: `fixture <name>: <type_expr> = <value_expr>;`, a module-level declaration terminated by `;` like every other non-block declaration (§2). Every argument of an `example` call in that module MUST be the name of one of its fixtures, so every example input has a declared origin.

| Rule | Detail |
|---|---|
| Value | A closed, deterministic literal of §2–§3 (`Int`, `Decimal`, `Text`, `Date`, `Duration`, `Bool` — `true`/`false`) or an id literal, or the name of another fixture of the same module. An id literal is either bare `#12`, whose type the fixture's declared type supplies (§3), or carries its ascription `#12 : Id<Task>`; the declared type MUST be `Id<T>` with one determined target, and an ascription MUST agree with it — a mismatch is `E-LIT-002` (§3). No capability use (no clock, no random), no rule or view call, no state read — a fixture replays identically on every run (P1, P3). |
| Type | A fixture's declared type MUST be the type of its value; a value that does not have the declared type is a type error, as for any other declared value (§3). |
| Acyclicity | Fixture references MUST be acyclic: no fixture may depend on itself, directly or indirectly. A reference cycle is an error, not a value. |
| Scope | Module-local. Usable only inside `example` declarations and fixture initializers of the same module; not exported by `use`; not part of the public contract, so §8's compatibility rules are unchanged. A fixture's own name MUST NOT collide with another module-level name; a fixture value naming another fixture of the same module is a reference to that fixture, not a collision. |
| Argument (input) | Every argument of an `example` call MUST be the name of a fixture of the same module. A literal or any other expression is not a valid example argument in v0.1 — there is no unnamed input. A fixture passed as an argument is a value, never a place, and its declared type MUST match the parameter type. The restriction is on `example` calls; a `prove` declaration is not an example run and is not subject to it. |
| Observation (`then`, `==`) | In an example's `then` observation or its `==` expected value, a fixture name is an ordinary identifier expression for its value: a value, never a place. Those positions are expressions over the state after the call, not inputs, so they are not restricted to fixtures. |
| Initial state | Every `example` runs against a fresh store: each declared `state` table is empty. A fixture is a module-level value, not a store row: it holds its declared value. v0.1 defines no source form for seeding state; stateful scenarios are the corpus semantics cases (`corpus/semantics/*.json`), whose format is unchanged. |

This settles S5 ([#15](https://github.com/developerz-ai/tessera/issues/15)): every example input has a declared origin.

Rule statements:

- `let x = e or fail Name;` binds, or aborts the rule with a named failure.
- `require p or fail Name;` checks a precondition.
- `new t: T where ...;` creates a value satisfying the constraints; the compiler solves for field values and MUST report unsolvable or ambiguous constraints.
- `place += e;`, `place -= e;`, `place = e;` declare the new state. All reads see the state before the rule (the snapshot); all writes apply at commit. There is no explicit `old` expression in v0.1.
- `output ledger += e;` buffers one stream element, without IO (§2.3, §5).
- `return e;` gives the result.

```tessera
needs clock: Clock;

fixture bob: Id<User> = #1 : Id<User>;
fixture alice_task: Id<Task> = #12 : Id<Task>;

rule complete(by: Id<User>, id: Id<Task>) needs clock {
  let t = tasks[id] or fail NotFound;
  require t.owner == by or fail NotFound;
  tasks[id].status = Done(clock.now) unless t.status is Done;
}
law done_once: forall t in tasks. t.status is Done => t.status.at >= t.created;
prove complete(by, id) is idempotent;
example complete(bob, alice_task) fails NotFound;
```

Why this shape: a rule is data about a state change, so the compiler can reorder, batch, and prove it. Imperative control flow is not needed.

## 5. Execution semantics

A program is a state machine: `(state, inputs) -> (state', outputs)`. The interpreter implements exactly this and is the reference for all backends.

1. **Atomic rules.** A rule call reads one snapshot, computes all changes, checks all laws that mention touched state against the proposed post-state, and commits or aborts as a whole. On abort, persistent state MUST remain unchanged: all proposed writes and buffered outputs MUST be discarded, and no success value is published. Inputs already appended to the input log MUST be retained, including inputs consumed by an aborted call. Why: laws only need checking at commit, and aborts leave no partial state while remaining replayable.
2. **Failures are values.** `fail Name` aborts the rule and returns a named failure. A caller sees `Ok(v)` or `Failed(Name)`. If any commit-time law check evaluates to false, the rule MUST abort and return `Failed(LawViolation)`, never `Ok(v)` or a panic. `LawViolation` is reserved for this runtime failure. `DivisionByZero` and `RefinementViolation` are reserved for the numeric and external-validation failures in §3. None of these names may be used as a user-defined failure name. All three failures obey the same atomic abort and input-log retention rules, including when validation rejects a request before rule entry. Why: laws can talk about failures, and error behavior is part of the spec.
3. **Total evaluation.** Expressions always terminate (no loops, no unbounded recursion; structural recursion over finite data only). Why: removes termination proofs and allows optimization.
4. **Fixed evaluation order.** Collection iteration order and arithmetic order are specified. Parallel execution MAY be used only when results are provably identical. Why: determinism across backends.
5. **Serial commits.** Rule calls on one store commit in a total order recorded in the input log. Concurrency is allowed only through partitioned state (shards) with independent logs. Why: replay and rollback.
6. **Input log.** Every external input (clock reading, random bytes, id generation, request) is appended to a log before use. Replaying the log reproduces the run exactly. Why: debugging production failures and offline sync.
7. **Resource bounds.** `bound` clauses and the standard library declare worst-case cost; exceeding a declared time or memory bound in the interpreter is a test failure.

Output: rules never perform IO. `output ledger += e;` buffers the value of `e` as one element of the declared stream (§2.3). Appends to each stream retain statement source order within a call, then the logged serial commit order across calls; backends MUST preserve this order. The surface delivers buffered elements only after a successful commit. An abort discards every buffered element along with proposed state writes; input logs remain unchanged by that discard. An output stream is not readable or writable state and cannot be assigned through an ordinary `place`.

**Execution scenarios (prose, not new syntax):**

- **Commit-time violation:** persistent balances start at 10 and 20. A rule consumes a logged request, proposes balances of -1 and 31, buffers a transfer notification, and computes a return value. A law requiring nonnegative balances evaluates to false on the proposed state. The result MUST be `Failed(LawViolation)`; persistent balances remain 10 and 20, both proposed writes and the notification are discarded, no output is delivered, and no `Ok(v)` or success value is published. The request remains in the input log.
- **Assume-admitted violation:** an executable law requiring a stored count to remain at most 10 has proof outcome Unknown and is explicitly admitted with `assume` (§10). Starting at count 10, a rule consumes a logged request and clock reading, proposes count 11, and buffers a notification. The law still executes at commit and evaluates to false. The result MUST be `Failed(LawViolation)`; the count remains 10, the proposed write and notification are discarded, no output or success value is published, and both logged inputs remain. Admission does not change Unknown into Proven.
- **Invalid request refinement:** a rule accepts `Int[0..100]`. A logged external request carrying `101` (likewise `-1`) MUST return `Failed(RefinementViolation)` before body execution, with no state writes, outputs or success publication. The rejected request remains logged. Requests carrying `0` or `100` pass this entry check and may run the body; other checks still govern commit.
- **Invalid capability result:** starting at count 9, a rule consumes a logged request, proposes count 10 and buffers a notification, then receives logged integer `101` from a capability declared to return `Int[0..100]`. Validation MUST fail before that integer is used as a refined value or narrowed for storage. The call returns `Failed(RefinementViolation)`; count remains 9, the write and notification are discarded, no success is published, and the request and capability input remain logged. An `assume` on the named refinement does not bypass validation.
- **Runtime zero divisor:** a rule proposes a write and buffers an output, then divides two `Decimal(2)` operands whose divisor comes from a logged input and equals `0.00`. Unless rejected statically under §3, the call MUST return `Failed(DivisionByZero)`, discard the write and output, publish no success and retain the logged inputs. Dividing by a statically known `0.00` instead prevents compilation.
- **Successful commit:** starting at count 9 under the same executable law, a rule proposes count 10 and buffers a notification. If all applicable law checks hold, the call commits count 10 and returns `Ok(v)`; only then may the surface deliver the notification. Logged inputs remain in the log.

## 6. Effects and capabilities

Nothing is ambient. A module can only use what it declares with `needs`, and the application grants those capabilities explicitly. Why: reviewing what code can do matters more when you did not write it.

| Capability | Gives | Determinism handling |
|---|---|---|
| `Clock` | `now`: `Instant`; `today`: `Date`, the UTC calendar date at the reading | Each reading is logged as an input; host time zone and DST MUST NOT affect results for the same logged inputs. |
| `Random` | `token(n)`, `int(a..b)` | Seeded from the log; replays identically. |
| `IdGen` | `next` | Logged, monotonic per store. |
| `Argon2`, `Hash`, `Sign` | Password and crypto primitives | Trusted code; listed by `tessera audit`. |
| `net.listen(port)`, `net.connect(host)` | Network access | Requests and responses are logged inputs. |
| `fs(path)` | File access | Reads are logged inputs. |
| `db: Db` | Access to a declared store, bound locally as `db` | Transactions follow §5. |

```tessera
needs clock: Clock, rng: Random, kdf: Argon2;
needs listener: net.listen(8443), files: fs("./data"), db: Db;
output ledger: Stream<Entry>;
rule record(entry: Entry) {
  output ledger += entry;
}
```

**Clock semantics (D2):** with `needs clock: Clock;`, `clock.now` yields an `Instant`, and `clock.today` yields the proleptic-Gregorian calendar `Date` of its reading in UTC. Neither operation may consult the host's local time zone or daylight-saving-time (DST) rules to determine its result. Each reading is a separately logged input (§5); separate `now` and `today` readings are not required to be simultaneous and may straddle a UTC day boundary.

**Time examples (prose, not Instant literals or conversion API syntax):**

- `let due = 2026-10-22;` binds a calendar `Date`, independent of any time zone. A logged `clock.now` reading at 2026-10-22 00:00:00 UTC is an `Instant`, not the value `due`, even though its UTC calendar date has the same year, month and day. Passing `due` where an `Instant` is required is a type mismatch, not an implicit midnight conversion.
- A `clock.today` reading just before the UTC boundary, at 2026-10-22 23:59:59 UTC, MUST yield `2026-10-22`; a reading at 2026-10-23 00:00:00 UTC MUST yield `2026-10-23`. These results MUST be the same on hosts configured for UTC or any other zone, including zones observing DST. Replaying those logged readings MUST preserve these dates.

The normative syntax is in §2: every capability reference has an explicit local binding before `:`. Thus `db: Db` replaces the schematic `store:Db`: `store` is reserved and cannot be a binding; `db` is the binding and `Db` names the store capability, not a value argument or a newly declared type parameter. Similarly, `listener` binds `net.listen(8443)` and `files` binds `fs("./data")`. Optional `<...>` supplies types and optional `(...)` supplies value expressions; the spelling alone does not grant access. The `[grant]` strings in §8 are manifest data, not source-language needs entries, and their syntax is unchanged.

Rules:

- A rule MAY declare `needs clock, rng` after its optional return type and before its body. Each name MUST resolve to a module-level capability binding, not a new typed declaration. An unbound name fails checking. Module bindings alone do not authorize a rule to use capabilities.
- The declared set is part of the rule's signature, so callers see which capabilities a call uses. Omitting the clause means the empty set; body usage MUST NOT infer or enlarge it. Unused declared capabilities are permitted and remain part of the signature even if optimization removes all uses. Declaration ordering is irrelevant. This settles S2: rule-level `needs` is expressed only by the header clause and is never inferred from the body.
- Every direct capability use MUST be covered by the rule's declared set. Every call MUST also be covered: all capabilities in the callee's declared set MUST occur in the caller's declared set, including requirements propagated through further calls. Missing requirements fail checking, even if the callee does not use them in its body.
- Calls are checked against the callee's published signature without inspecting dependency bodies. Requirements are compared by resolved capability identity, not local spelling: a caller's local alias MUST resolve to the capability required by the callee; equal names in different modules do not establish a match.
- The compiler MUST preserve declared capability sets in Core IR and public signature metadata so callers and compatibility tooling observe the same contract. These are sets of resolved identities: header order and local binding spellings MUST NOT affect the normalized contract or its hash (§8).
- The application MUST explicitly grant required capabilities. A dependency can only use capabilities listed for it in the app's `[grant]` table; insufficient grants fail checking and the build. A rule header does not confer a grant.
- Views remain pure: they MUST NOT use capabilities directly or call rules requiring them.
- User-written `foreign` declarations (C or system libraries) are deferred: `foreign` is reserved and unsupported in v0.1 (§2.3). A `foreign` declaration, where a later version supports one, MUST be marked trusted, is excluded from proofs, and is listed by `tessera audit`; trusted capability implementations, including crypto wrappers, remain outside proofs and MUST be listed by `tessera audit`.
- `Secret<T>` values cannot flow into log, output, a surface response, or a store column unless that column is declared `Secret`. This is checked by a static information-flow pass (see §10 for limits).

For example, these rules use a module binding and propagate its requirement explicitly:

```tessera
needs clock: Clock;

rule read_time() -> Instant needs clock {
  return clock.now;
}
rule forwarded_time() -> Instant needs clock {
  return read_time();
}
```

Invalid: the omitted clause declares the empty set, so the call fails checking even though the module binds `clock`:

```tessera
needs clock: Clock;

rule read_time() -> Instant needs clock {
  return clock.now;
}
rule missing_need() -> Instant {
  return read_time();
}
```

The same coverage rule rejects a direct `clock.now` use in a rule with no needs clause. It also rejects a caller declaring only `clock` when its callee declares both `clock` and `rng`, even if that callee never reads `rng`. Conversely, a caller declaring both requirements may call a callee declaring only `clock`. Across modules, bindings named `clock` and `time_source` match if they resolve to the same required capability identity; two bindings both named `clock` do not match if their resolved identities differ. This comparison does not define any new parameterized-capability or grant semantics.

A public rule's declared set is a published contract: adding, removing or replacing a resolved capability MUST require a major version bump (§8), including removal of an unused declaration. Reordering alone does not change that set.

These headers do not change §5's input-log requirement: each external input MUST be logged before use.

Why: capability-style effects give the same review benefits as an effect system with much less machinery, and every effect is a logged input, so runs can be replayed and tests can mock them.

## 7. Stores and surfaces

The domain module holds all logic. Stores and surfaces are wiring only and MUST NOT contain business logic. Why: one reviewed core serves every platform.

**Store** binds state to storage:

```tessera
store db = sqlite("app.db") migrate checked;
```

- v0.1 targets SQLite. Table schema, `CHECK` constraints from refinements, and indexes are generated from types and `index` hints.
- Each rule runs in one transaction; commit equals rule commit.
- `migrate checked`: a changed type produces a migration only if a total, checked `migrate` function exists or the change is provably lossless; otherwise the build fails.

**Surface** maps platform events to rule calls and views to output:

```tessera
surface http :8443 {
  POST /login (email, pw) => auth.login;
  scope authed(auth.principal(cookie sid)) {
    POST /tasks (title, due?) => todo.add(me, title, due);
    GET  /tasks               => todo.agenda(me.id);
  }
}
surface cli "todo" { add <title> => todo.add(me, title); ls => todo.agenda(me.id) as table; }
```

| Surface | v0.1 | Notes |
|---|---|---|
| `cli` | Required | Static binary, argument parsing generated. |
| `http` | Required | Auth, CSRF, rate limits declared; unauthenticated calls to `scope authed` return 401 automatically. |
| `web` | Milestone 5 | Compiled to Wasm plus a small JS shim; offline-first by replaying the rule log. |
| `gui`, `mobile`, `game` | Later | Native bindings per platform; same rules. |

Generated adapters and decoders MUST check external refined integers as specified in §3 before supplying rule arguments, exposing capability results as refined values, or narrowing them into storage. An integer that decodes successfully but lies outside `Int[a..b]` is a refinement failure, not a successful decode into that refined type. Store `CHECK` constraints do not replace this boundary validation. Request rejection before entry and capability-result rejection mid-rule MUST preserve §5's failure, rollback and log semantics; adapters MUST NOT turn either into a successful rule response. This specifies neither wire encodings nor new HTTP status codes.

**App manifest** ties them together:

```tessera
app todo { use todo, auth, db; surfaces http, cli; target native, wasm; }
```

## 8. Packages, hashing and loading

> **Amended:** dependency declaration, resolution, release and mirroring are specified in [packages.md](packages.md) (git URL + tag, no central registry). Hashing, store layout, proof re-checking and loading below still hold.

Identity is a hash; names are labels. A definition's identity is the BLAKE3 hash of its normalized Core IR, so renaming or reformatting changes nothing. Why: exact caching, semantic diffs, reproducible builds, no dependency resolution conflicts.

```toml
# tessera.toml
[package] name = "todo-app" version = "1.0.0" edition = "2026"
[deps]  auth = "2"  sqlite = "4"
[grant] auth = ["clock", "random", "store:db"]  sqlite = ["fs:./app.db"]
```

- **Lockfile** (`tessera.lock`) pins every dependency to a hash, and the compiler version to a hash.
- **Store:** `~/.tessera/store/<hash>` holds IR, proofs and metadata. Build artifacts are cached by `(hash, target, flags)`.
- **Compatibility check on release:** removed or changed public signatures and weakened laws require a major bump. A public rule's declared capability set (§6) is part of its signature: any addition, removal or replacement MUST require a major bump, even when removal reduces required power. Reordering alone is not a capability-set change. Compare declared sets by resolved capability identity, not local binding spelling or capabilities inferred from bodies; unused declarations remain in the public contract. For example, changing `{Clock}` to `{Clock, Random}`, reversing that change, or replacing `{Clock}` with `{Random}` requires a major bump; reordering `{Clock, Random}` to `{Random, Clock}` does not. These braces illustrate identity sets, not source syntax. Renaming a local binding without changing its resolved identity likewise does not change the set or its normalized hash. Signature metadata records requirements, not application grants (§6). When the solver cannot decide, release MUST fail safe and require a major bump.
- Different versions coexist as different hashes. Values crossing between two versions need an explicit, total `adapt` function.
- Consumers re-check proofs; a package's proof claims are never trusted. Proof certificates SHOULD be cached by hash.
- **Loading:** `tessera dev` loads IR by hash into the interpreter and may hot-reload rules in place (dev only). `tessera build --release` links whole-program, statically. Dynamic shared libraries are not supported in v0.1.
- **Plugins** (optional, later): sandboxed Wasm components with declared capabilities and resource limits.
- **Commands:** `add`, `update`, `audit`, `vendor`, `release`, `why-dep`.
- **Registry:** none — there is no central registry and no upload step. A release is a signed annotated tag `v<version>` in the package's own repository, fetched by URL and tag: `tessera release <version>` runs the full check, diffs compatibility against the previous tag (blocked without a major bump), writes `tessera.release.json`, then creates and pushes that tag. *(Superseded — see [packages.md](packages.md).)*

Why no shared libraries: generic code is specialized per use site, whole-program optimization needs to see both sides, and shared libs break the same-hash-same-behavior rule.

## 9. Compiler architecture

One typed Core IR is the only input to the interpreter, the verifier and the optimizing pipeline; there is no JIT and no second front end.

```
source ─▶ AST ─▶ Core IR (typed, hashed) ─┬─▶ Interpreter (oracle)
                                          ├─▶ Verifier (SMT)
                                          └─▶ Dataflow IR ─▶ Low IR ─▶ C / Wasm / LLVM IR
```

Every backend MUST match the interpreter on every example, and the verifier gates release builds.

- **Core IR:** typed, pure, effects explicit, hashed. Every other stage reads only this.
- **Interpreter:** compiles Core IR to compact bytecode or closures over indexed in-memory tables. It is the semantic oracle and the dev loop. Target: re-check and run a changed rule in tens of milliseconds.
- **Dataflow IR:** fusion, incremental views, index selection and e-graph rewriting via `egg`. Halide-style scheduling separate from the algorithm is a future direction, not v0.1 source syntax: `schedule` is reserved and unsupported (§2.3). Why: pure, alias-free code lets the compiler do what C++ compilers must avoid.
- **Low IR:** at most about 50 instruction kinds, explicit memory, loops and SIMD, no undefined behavior, wrapping or checked arithmetic spelled out.
- **Backends:** emit C and call clang first, then direct Wasm, then LLVM IR for release builds. No custom machine-code backend and no JIT in v0.1. Why: matching LLVM across architectures is not realistic; the edge is the layer above it.
- **Determinism:** no fast-math, canonical NaN, defined overflow. Compiler version, target and flags are part of the build cache key.
- **Performance expectations** (to test in M4 and M6, not measured): I/O-bound apps near parity with C++; data-parallel and analytical code can win; a first-generation optimizer may be 1.5x to 3x slower on compute-heavy code.

## 10. Verification

Laws and `prove` goals are discharged by an SMT solver (wrap Z3 or cvc5; never write a solver). The result is one of three outcomes, and the compiler MUST NOT treat the third as success.

| Outcome | Meaning | Build result |
|---|---|---|
| Proven | The solver shows the law holds for all inputs. | Pass; certificate cached by hash. |
| Refuted | The solver found a counterexample. | Fail with a concrete failing state and call. |
| Unknown | Timeout or undecidable. | Fail unless the owning declaration carries explicit `assume` (§2.3); every admission is listed by `tessera audit`. `hint` is unsupported and cannot admit Unknown. |

- **Decidable fragment:** v0.1 laws are limited to linear integer and decimal arithmetic, booleans, equality, sets, maps, and bounded quantifiers over `Table` rows. Anything else needs `assume`. Why: predictable solver behavior beats expressiveness.
- **Numeric model:** proofs MUST model §3's mathematical integers, inclusive refinement bounds, and per-operation fixed-scale decimal rounding, including signed half-even ties and division-by-zero failure. Exact rational arithmetic without the required rounding is not a sound substitute. If the solver cannot encode or discharge an obligation involving these operations, its outcome MUST be Unknown, never Proven from an unrounded approximation. External refined inputs may be treated as satisfying their declared bounds only after the mandatory validation boundary; proofs MUST preserve the invalid-input failure paths.
- **Assumptions:** a trailing `assume` on a type, law or prove declaration (§2.3) admits that declaration's Unknown proof obligations; it never admits Refuted obligations or waives type checking, examples, resource checks, external refinement validation or numeric failure checks. It does not establish a proof or change Unknown into Proven. `tessera audit` MUST retain the owning declaration, marker span, admitted obligations and their Unknown status, even when the build is admitted. An executable law admitted with `assume` MUST retain the commit-time checks in §5 and MUST return `Failed(LawViolation)` if a check evaluates to false. This does not require runtime checks for non-executable claims, such as timing claims without a specialized checker.
- **Fast mode** (`tessera dev`, `tessera check --fast`): type checking, examples, and counterexample search with short timeouts. It can miss violations but MUST NOT report false proofs.
- **Full mode** (`tessera build --release`, CI): all laws and proofs MUST pass verification or be explicitly admitted with `assume`; admission is not a Proven result.
- **Parity check** (`tessera check --parity`): every example runs through the interpreter and the compiled output and MUST be bit-identical.
- **Information flow** (`Secret`) and timing claims (for example, constant-time login) are NOT SMT problems. v0.1 implements Secret flow as a static taint analysis. Timing claims without a specialized checker remain Unknown and require an explicit trailing `assume` on their owning declaration to admit the build; there is no automatic admission. This does not introduce additional timing-goal syntax. Do not promise more.
- **Trust boundary:** the solver, the interpreter, trusted built-in capability code, and the assumed facts. `tessera audit` MUST list all of them.

Why: a proven law that encodes the wrong requirement still ships the wrong behavior. Laws are short and are what humans review.

## 11. Diagnostics and CLI contract

Every diagnostic MUST exist in human form and as JSON (`--json`). Why: the agent loop depends on structured, actionable feedback.

```json
{ "code": "E-LAW-001", "severity": "error",
  "law": "todo.isolation", "rule": "todo.complete",
  "span": { "file": "todo.tes", "line": 31, "col": 3 },
  "counterexample": { "state": { "tasks": [ { "id": 1, "owner": "alice" } ] },
                      "call": "complete(by: bob, id: 1)",
                      "effect": "tasks[1].status changed by bob" },
  "hint": "add `require t.owner == by or fail NotFound;`" }
```

Diagnostic rules: stable codes, exact spans, a minimal counterexample when one exists, at most one suggested fix, no cascading errors from the same cause.

| Command | Purpose |
|---|---|
| `tessera dev` | Interpreter, hot reload, fast-mode proofs, REPL (`why <view>` prints a derivation tree). |
| `tessera check [--fast\|--full\|--parity] [--json]` | Type check, proofs, examples, parity. |
| `tessera fmt` | Canonical formatter (idempotent). |
| `tessera build [--release] [--target t]` | AOT build. |
| `tessera fill <hole>` | Asks a configured model to fill a typed hole `?name`, accepts only candidates that pass checks. |
| `tessera add \| update \| audit \| vendor \| release` | Packages (§8, [packages.md](packages.md)). `release` tags a release: full check, compat diff (blocked without a major bump), writes `tessera.release.json`, creates and pushes a signed annotated tag `v<version>`. No upload step. |

Typed holes: `?name` in a rule body is legal in dev mode and an error in release builds. The compiler reports the hole's expected type, `needs`, touched state and the laws in scope. Why: humans write the skeleton and machines fill the body, each checked.

## 12. Minimum standard library

Keep v0.1 small enough for the whole library to fit in a model prompt. Everything is pure except capability handles.

| Module | Contents | Why |
|---|---|---|
| `core` | `Maybe`, `Result`, `Bool`, comparison, `min`, `max` | Foundation. |
| `num` | `Int`, `Decimal`, `F64` operations under §3: mathematical integer arithmetic, fixed-scale half-even decimal operations and no implicit numeric conversions; numeric failures follow §5 | Determinism. |
| `text` | UTF-8 operations, `matching` patterns (RE2-style, no backtracking), formatting | Safe, predictable regex. |
| `list`, `set`, `map` | `map`, `filter`, `fold`, `sum`, `count`, `sort_by`, `group_by`, `join` | Replaces loops. |
| `table` | Query operators (`where`, `find`, `order_by`, `join`) that compile to SQL | Index selection. |
| `time` | `Instant`, `Date`, `Duration`, calendar arithmetic (UTC only in v0.1) | No time-zone surprises. |
| `json`, `csv` | Total encode and decode with typed results | Surface payloads. |
| `crypto` | Wrappers for `Argon2`, `Hash`, `Sign`, `Random` (trusted) | Audited primitives only. |
| `test` | `example` runner, fixtures, mock capabilities, log replay | Free tests. |

**Time scope (D2):** v0.1 instant/calendar operations MUST use UTC whenever a time-zone interpretation is needed, including determining a calendar date from a clock reading. `Date` itself remains a zone-independent proleptic-Gregorian calendar date (§3), not an instant at UTC midnight. Host time-zone settings and DST MUST NOT change results for the same state and logged inputs. Non-UTC time zones and their DST rules are deferred beyond v0.1. This fixes the time-zone scope, not a new conversion API or an `Instant` literal syntax.

Rule: no module may add a capability that is not declared in its header.

**Package scope (K2, [#19](https://github.com/developerz-ai/tessera/issues/19)):** WP J MUST implement registry-free git dependency resolution, lockfile and audit alongside hashing and content-addressed package storage, as specified in [packages.md](packages.md). Its package store is distinct from WP E's application store. No central registry is required. Any discovery index MUST be an optional git repository mapping short names to URLs and MUST NOT be required for dependency resolution. This scope clarification leaves hash normalization unchanged.

Freeze first, in this order: AST schema, Core IR schema, diagnostics JSON, semantics test-suite format, Low IR schema, hash normalization.

Swarm rules:

- Tests and the example corpus come before implementation. Spec ambiguity is filed as an issue to the spec owner, never guessed.
- Each agent owns one crate. A change to a frozen interface needs a versioned proposal and a green differential-test run.
- Nothing merges unless interpreter versus backend parity is green.
- The agent that designs a feature does not also review it.

Milestones, each with a gate:

1. **M0 Spec and corpus.** 20 example programs and the semantics cases written. Gate: human sign-off on laws and examples.
2. **M1 Interpreter (A, B, C).** The todo domain runs in the REPL. Gate: all examples pass.
3. **M2 Verifier (D).** Laws on todo and auth proven or refuted. Gate: zero false proofs on a seeded-bug suite.
4. **M3 Store, CLI, HTTP (E, F).** Todo app with auth runs on SQLite. Gate: end-to-end tests and store parity.
5. **M4 AOT via C (G).** Gate: parity on every example, and the first benchmark against the interpreter.
6. **M5 Wasm and web (H).** Gate: browser build passes the same examples.
7. **M6 Optimizer and packages (I, J).** Gate: parity kept while benchmarks improve; hash stability proven.

## 14. Open questions and risks

The syntax and semantics above are a design, not a verified implementation. Nothing here has been compiled or benchmarked, and speed claims versus C++ are expectations to test in M4 and M6.

| Risk or question | Why it matters | Mitigation |
|---|---|---|
| Solver timeouts on valid laws | A correct program fails to build | Restrict to the decidable fragment; explicit, audited `assume` admission (§2.3), never a proof; `hint` unsupported; certificate caching |
| Specs can be wrong | A proven law can encode the wrong requirement | Human review of laws and examples; example corpus; mutation testing of laws |
| Hash normalization bugs | Equivalent programs hash differently, or different ones collide | Versioned normalization spec; property tests; reject unknown IR versions |
| `new ... where` solving | Ambiguous or unsolvable constraints | Require uniquely determined fields in v0.1; otherwise a compile error |
| Sharding and concurrency | Serial commits limit throughput | v0.1 is single-writer per store; design shard keys before M6 |
| Information flow and timing proofs | Not SMT problems | Secret taint analysis only; unchecked timing claims remain Unknown and need explicit `assume` admission |
| No training data for the language | Models write it less reliably | Keep syntax close to Rust and TypeScript; ship the spec plus 50 to 100 examples; compiler-in-the-loop with holes and counterexamples |
| FFI and crypto boundaries | Proofs stop at trusted code | Few, small, audited built-in wrappers; list in `tessera audit`; user `foreign` syntax deferred |
| Static linking of everything | Security fixes need rebuilds | `tessera audit` flags builds using a superseded hash |
| Open choices | Need a human decision before M0 | Postgres in v0.1 or later; exact `where` fragment; whether `tessera fill` ships in v0.1 |

**Settled scope (D2):** v0.1 instant/calendar operations MUST use UTC whenever a time-zone interpretation is needed (§12); non-UTC zones and their DST rules are deferred beyond v0.1. `Date` is a zone-independent calendar date, never an implicit midnight `Instant` (§2–§3). `Clock.now` yields `Instant`; `Clock.today` yields the UTC calendar `Date` (§6). UTC-only time is not an open choice.
